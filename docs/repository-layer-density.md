# Repository layer density (MOO-69 Commit 7)

Records current node/edge behavior for the repository layer after MOO-69's
adaptation to GraphIR, and explicitly defers density judgment/remediation to
the Garrison Step (MOO-44), per MOO-66's own scoping ("Repository-density
judgment... remain in MOO-44 unless construction encounters a truly
blocking failure"). No density/reduction work was added in MOO-69 beyond
what already existed — this is a documentation-only commit.

same harness `tests/repository-graph-adapter.test.mjs` uses) for each

|---|---|---|---|
| `golden-world` | 6 | 6 | 2 |
| `web-app-world` | 16 | 3 | 14 |
| `security-precision-world` | 19 | 0 | 12 |
| `vault` | 7 | 9 | 1 |

All four are small (single-digit to low-double-digit node counts) — none of
these fixtures exercise the repository layer at a scale where density
becomes a real usability concern. They exist to validate correctness
(schema validity, field mapping, edge kind distinction), not to stress-test
rendering at scale. No fixture currently in this repository is large enough
to evaluate real-world density behavior; that evaluation, on an actual
large repository, is explicitly deferred to the Garrison Step (see below).

## Existing reduction/filtering behavior (preserved, not modified)

MOO-69 did not touch any of CodeFlow's pre-existing density controls —
they continue to apply identically whether the render input is the legacy
analysis object or a repository-layer GraphIR (see
`src/render/repositoryRenderModel.js`):

- **Repository ingestion caps** (`index.html`'s `ANALYSIS_LIMITS`):
  `repoSoft: 300`, `repoMax: 750` for a GitHub-backed repository (a warning
  notification above 750, and the API sample is truncated to 750 files
  regardless); `localSoft: 500` for local-folder/zip analysis. These bound
  how many files ever become analyzed at all, upstream of the GraphIR
  adapter.
- **Folder filtering** (`folderFilter`): narrows the rendered node set to
  one folder (and its subfolders) at a time — `buildRepositoryRenderModel`
  applies this identically for both input shapes.
- **Adaptive rendering for large graphs** (`src/render/repositoryGraph.js`):
  once `nodes.length > 300`, the force simulation uses a faster
  `alphaDecay`/`velocityDecay`, and per-node text labels are hidden unless
  `graphConfig.showLabels` is explicitly on (reduces DOM/layout cost, not
  node count itself) — untouched by this issue's adapter work.
- **View-mode alternatives** (`graphConfig.viewMode`: force/radial/
  hierarchical/grid/metro) already exist as different spatial layouts for
  the same node/edge set — a partial answer to "how do I make a dense graph
  legible" that predates MOO-66/68/69 entirely.

## Garrison Step handoff notes

The following are **not** implemented and are explicitly deferred to
MOO-44 (Garrison Step) or a follow-on issue it proposes, per MOO-66's own
ownership rule that repository-density judgment stays there unless the
repository layer is genuinely unusable during construction (it is not —
see fixture counts above):

- **Clustering** — collapsing groups of related files into a single
  representative node above some density threshold. `GraphIR`'s `groups`
  array (folder-based today) is the natural extension point for this; no
  clustering logic exists yet.
- **Neighborhood isolation** — showing only a selected node's direct
  (or N-hop) neighborhood rather than the whole graph. `blastRadius`
  (`calcBlast`) already computes the data this would need (affected/
  transitive dependents), but nothing currently uses it to *filter* the
  rendered node set — only to annotate the detail panel.
- **Changed-files-only mode** — rendering only the files a PR/diff touched,
  as a first-class view rather than the current highlight-only treatment.
  MOO-69 Commit 5 added changed-area *markers* (a rendering hint — see
  `changedPaths` in `renderRepositoryGraph`) specifically scoped to avoid
  building this: highlighting is additive and low-risk; filtering the node
  set to changed-files-only is a real product decision (does context
  outside the diff disappear entirely, or dim?) that belongs with the
  Garrison Step's broader density judgment, not decided unilaterally here.
- **Blast-radius reduction** — using `calcBlast`'s impact score to
  progressively hide low-impact nodes at high density, rather than always
  rendering every file.
- **Node budgets** — a hard per-render cap independent of the existing
  ingestion-time caps (`ANALYSIS_LIMITS`), e.g. "render at most N nodes,
  prioritized by some relevance score," for repositories that pass
  ingestion but are still visually overwhelming at full density.

Each of these is a real design decision (what gets hidden, what "related"
means for clustering, whether reduction is automatic or user-toggled) that
the Garrison Step is positioned to make with actual usage evidence from
real, large repositories — building any of it speculatively now, against
fixtures too small to validate the choice, would be exactly the kind of
premature judgment MOO-66 scopes away from MOO-69.
